# Native shell (WinUI 3) — bridge layer

Work in progress: the port of the client UI from Tauri/WebView2 to native
WinUI 3. The Rust core is shared; only the UI changes.

```
client/core/   hopon-core: connection, state, cache, voice; no UI toolkit.
               All commands: hopon_core::api (typed fns + api::call by name).
client/ffi/    hopon-ffi: C ABI over the core → hopon_ffi.dll.
               bindings/NativeMethods.g.cs is generated by build.rs (csbindgen).
client/native/
  HopOn.Interop/       C# wrapper: HopOnCore.Start / Subscribe / CallAsync, typed
                       models (Models.cs), message merge (MessageMerge.cs) and
                       formatting (Rich.cs). No UI code: testable on Linux.
  HopOn.Interop.Tests/ models vs Rust fixtures, merge rules, Rich vs rich.ts.
  HopOn.BridgeCheck/   end-to-end check: C# → hopon_ffi → a real server.
  HopOn.App/           the WinUI 3 app (Windows App SDK, unpackaged, self-contained).
  fixtures/            events.json (from Rust), rich.json (from rich.ts).
```

## Keeping the two shells in step

- **Events and results**: `client/core/tests/event_fixtures.rs` writes one sample
  of every event to `fixtures/events.json` (`UPDATE_FIXTURES=1 cargo test -p
  hopon-core --test event_fixtures`); the C# models must parse each one with
  unknown members rejected and every member required, and round-trip it.
- **Formatting**: `client/ui/test/rich-corpus.mjs` runs the real `rich.ts` over
  ~4500 inputs into `fixtures/rich.json`; `Rich.cs` must match every output.
- **Message merge**: `MessageMerge.cs` ports `merge.ts` (in place, for the
  virtualized list) with the same tests.

## The bridge

- `HopOnCore.Start(host, dataDir)` boots the core (null dataDir = the same
  folder the Tauri build uses, so sign-in and cache carry over).
- `Subscribe("main", handler)` streams events: JSON objects tagged by `"t"`,
  the same shapes as `client/ui/src/types.ts`.
- `CallAsync(name, args, blob)` runs a command: the same names and camelCase
  arguments as the webview's `invoke` calls (`client/ui/src/ipc.ts`); errors
  throw `HopOnException` with the core's message. `blob` carries file bytes
  for `upload_file` (`{name, w, h}`), `set_avatar`, `set_banner`.
- Handlers and host callbacks run on core worker threads: marshal to the UI
  thread, don't block, and don't call back into the bridge from inside them.
  Exception: a subscription's first events (prefs, session snapshot, anything
  buffered) arrive synchronously inside `Subscribe`, on the calling thread.
- `IHopOnHost.MainHidden` is read for every event, off the UI thread: return a
  cached flag the UI thread keeps current.

Window-level features stay in each shell: zoom, fullscreen, tray,
notifications, the overlay window, the games webview.

## Checks

Linux (what CI can run; needs the dev server from `scripts/dev-up.sh`):

```
cargo build -p hopon-ffi --no-default-features
cd client/native/HopOn.BridgeCheck && dotnet build
HOPON_URL=ws://127.0.0.1:8080/ws LD_LIBRARY_PATH=../../../target/debug \
  dotnet bin/Debug/net10.0/HopOn.BridgeCheck.dll owner /tmp/bridge-check
```

It also passes as a Native AOT binary (`dotnet publish -r linux-x64
-p:PublishAot=true`, 2.9 MB, no trim/AOT warnings).

Windows DLL (cross-built from Linux like the rest of the client):
`cargo xwin build --release --target x86_64-pc-windows-msvc -p hopon-ffi`
→ `hopon_ffi.dll`, 28.5 MB with voice (libwebrtc), about the size of today's
`hopon.exe`.

The WinUI app's C# (not its XAML) also compiles on Linux against the real
WinUI reference assemblies: `scripts/native-check-linux.sh`.

## CI (`.github/workflows/windows-native.yml`, windows-latest)

- **bridge**: builds `hopon_ffi.dll` (with voice), the server and `e2e_feed`;
  model tests; the bridge check against a server on the runner (JIT and AOT).
- **app**: builds and publishes the WinUI app (Native AOT), then
  `scripts/ci/measure-app.ps1`: startup (`--perf-exit`, 5 runs), remote message
  → painted latency (`e2e_feed`, 200 messages), idle CPU and RAM, size (also
  LZMA-compressed, like an installer) and a screenshot. Results are in the
  run's summary and the `native-app-results` artifact; the app itself is the
  `HopOn-native-preview` artifact.

## Measurements (windows-latest CI runner, 2026-11-16)

From `scripts/ci/measure-app.ps1`: a GitHub-hosted Windows VM (no GPU, WARP
rendering), app published with Native AOT and the **release** core DLL, server
on the same machine. Not a user's PC: a check of the targets, not final numbers.

| item | native WinUI (two runs) | target | Tauri build (README) |
|---|---|---|---|
| process start → first frame, 5 runs | median 144–177 ms, worst 264–342 ms | < 1 s | 657 ms |
| remote message → painted, 200 msgs at 20/s | p50 20–22 ms, p95 23–35 ms | < 100 ms LAN p95 | 28.7 ms (Linux, software GL) |
| idle CPU, 30 s | 0.03–0.12 % of all cores | < 1 % | 0.13 % |
| idle RAM | 68–71 MB private, 129 MB working set | < 200 MB | 190 MB private |
| installer estimate (LZMA2 of everything shipped) | 21.8 MB | < 30 MB | 10.5 MB |

Where the size goes (uncompressed, 92.7 MB): the core DLL (libwebrtc) 27.2 MB,
WinUI/Windows App SDK runtime ~50 MB (`Microsoft.ui.xaml.dll` 14.5 MB, Controls
7.1 MB, composition DLLs ~9 MB), `HopOn.exe` (Native AOT) 7.4 MB.
